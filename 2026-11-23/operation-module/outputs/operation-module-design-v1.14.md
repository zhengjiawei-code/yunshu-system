## 1. 模块概述

### 1.1 业务定位

运营管理是"客户下单 → 网点接单 → 运单形成 → 后续运输/到货/签收/财务"链路的起点。本轮只做两件事：

1. **开单揽收（公司内部端）**：网点人员自行开单，或承接客户在客户端提交的预开单后接单并确认揽收，形成正式运单。
2. **运单管理（公司内部端）**：按数据权限查询本机构及授权范围内的运单，查看详情、导出、按规则作废。

### 1.2 边界（明确不做）

| 不做 | 归属 |
|---|---|
| 预开单的客户自助填写页 | 客户端（菜单 1201，`portal_type=CLIENT`）；**预开单表与接单接口由本方案提供**，客户页面不在本期 |
| 运单导入、删单明细 | 运营管理下 1203 / 1205，另立方案 |
| 装车配载、到货卸车、提货、派送、签收 | 各自模块；本方案只预留状态与字段 |
| 财务核销、对账、结算 | 财务模块 |
| 打印模板、标签打印 | 后续单独方案；本方案只保证路由节点的 `warehouse_area` 等打印要素被快照 |
| 客户管理完整档案 | 已由家伟定稿：先建简易客户表，客户管理模块后期补全 |

### 1.3 角色与入口

| 角色 | 入口 | 能做什么 |
|---|---|---|
| 网点开单员 | `/operation/create` | Tab1 自行开单；Tab2 查看/接单/退回/确认揽收本网点预开单 |
| 网点管理员 | `/operation/create`、`/operation/waybill` | 上述全部 + 本网点运单查询/作废；可接下属开单员已接但未揽收的预开单 |
| 分公司管理员 | 同上 | 在本公司管理范围内开单、接单、查运单（含下属网点） |
| 总部管理员 | 同上 | 全部机构开单、接单、查询、作废 |
| 客户账号 | 不进入本模块 | 只使用客户端预开单（菜单 1201，`portal_type=CLIENT`） |

两个 Tab 的职责边界固定为：**预开单的创建归客户端自助入口，接单与正式开单归公司内部端（本页）**。内部端不提供"代替客户发起预开单"的入口，避免两边都能创建造成来源混乱。

菜单已在 `V2__init_sys_menu_seed.sql` 中存在，本方案**不新增菜单**；按钮权限点见 11.3，落地时由菜单管理页维护。三个角色的可见范围与操作差异见 10.6。

## 3. 页面设计

### 3.1 开单揽收页（`/operation/create`）

#### 3.1.1 Tab 结构与业务关系（v1.1 定稿）

页面顶部两个 Tab，**默认激活 Tab1「开单揽收」**：

| Tab | 数据来源 | 行为 | 与另一 Tab 的关系 |
|---|---|---|---|
| **Tab1 开单揽收**（默认） | 无 | 空白表单 → 开单员录入 → 保存生成运单 | 与 Tab2 共用同一套表单组件、字段分组与校验；仅"来源条"和客户字段只读性不同 |
| **Tab2 预开单揽收** | `biz_pre_waybill`（客户客户端提交） | 预开单列表筛选 → 选中「接单」→ 带出申报数据 → 核对补录 → 「确认揽收」生成运单 | 确认揽收后预开单状态置 30 并回写运单号；表单清空并回到列表空态 |

职责边界：**预开单归客户端自助入口，开单揽收归公司内部端**；内部端不提供"代客户发起预开单"。两者不合并为同一张列表，原因是接单是"处理待办"、自行开单是"直接录入"，节奏与入口不同。

Tab 布局与切换：

- Tab 条固定在页头下方；Tab1 只显示表单区；Tab2 显示「预开单列表卡片 + 表单区（接单后展开）」。
- 切换 Tab 时**各自保留草稿**：离开前用 `captureForm()` 快照当前表单（字段值、费用、支付、路由选择、来源预开单号），回来时 `restoreForm()` 还原；不因切换丢失已录入内容。
- 未保存提示：当前 Tab 表单有内容（或处于接单中）时切换，弹二次确认"当前页有未保存内容，切换后将保留草稿，是否继续？"；取消则留在原 Tab。
- Tab2 未接单时表单区隐藏，显示空态"请选择预开单并接单"；接单后表单在列表下方展开，页面滚动定位到来源条。
- 默认激活判定：进入页面固定落 Tab1；从"运单管理 → 查看预开单"等外部入口进入时，允许通过 `?tab=pre` 指定 Tab2，无参数一律 Tab1。本期原型不做外链跳转，只做页面内切换。
- 确认揽收成功后：清空草稿、退出接单态、表单区收起、列表刷新，并提示"已回到预开单列表，可继续接单"；不自动跳回 Tab1，避免打断连续接单。
- 「重置」在 Tab1 清空表单；在 Tab2 接单态下改为「恢复申报信息」（恢复为该预开单原始申报值，需二次确认）。

一屏约束与验证口径：

- 目标：1600×900 下 `document.documentElement.scrollHeight ≤ clientHeight`；1440×900 同样满足。底部操作条与最后一个分区必须在视口内。

布局规则：
- 页面本身不滚动；`#formArea` 为唯一滚动容器，底部操作条 `position: sticky; bottom: 0` 常显。

- Tab2 接单后客户名称仍由发货人匹配结果只读展示，不锁定发货人（允许补录纠正）。

#### 3.1.4 客户名称由发货人自动带出（v1.4 定稿）

开单页**不再录入客户名称、客户电话，也不提供客户选择器或快速新建**。客户名称改为发货人的匹配结果，只读展示在发货方卡片内。

| 项 | 规则 |
|---|---|
| 触发 | 录入/修改发货人后 250ms 防抖匹配；发货电话变化时重新匹配；失焦立即匹配 |
| 匹配键 | ① 发货人名称与 `biz_customer.customer_name` **精确相等**；② 同名多条时用发货电话与 `customer_phone` 精确匹配；③ 命中唯一记录即选中 |
| 同名歧义 | 名称相同、电话也未提供或都不匹配时，不自动猜；在发货方卡片内浮出候选（客户名称 + 电话 + 单位），由开单员按电话点选。仍未选择则视为未命中，留空 |
| 命中展示 | `客户名称 + 联系电话 + 客户编号`，右侧「已匹配」标签；纯只读文本，不可手改（改发货人/电话会自动重算） |
| 未命中 | 客户名称显示占位 `—`，**不提示、不弹窗、不拦截**，开单可正常保存；**不显示红星、不加浅红底**，因为这不是用户漏填 |
| Tab2 | 发货人来自预开单申报，带入后同样匹配；命中显示，未命中留空，不锁定发货人，允许补录纠正 |
| 落库 | 命中：`customer_id` + `customer_name`/`customer_phone` 快照；未命中：`customer_id` 为空，`customer_name`/`customer_phone` **留空**（不按发货人回填） |
| 列表与导出 | 保留客户名称列，取运单快照；未命中的运单该列显示 `—`，不影响筛选其他列 |

为什么未命中不按发货人回填：`customer_name` 的语义是客户档案名称，与 `sender_name`（发货人）是两个字段；混用会让后续客户管理、对账、客户维度统计出现"假客户"。发货人本身已落在 `sender_name/sender_phone`，信息不丢失，因此留空更干净。未命中不影响开单，是因为开单的最高优先级是"先把货收进来"，客户档案的补建不应阻塞一线。

为什么开单页不做客户新建：客户主数据应有唯一维护入口与审核口径，开单页只做只读引用，避免两处建档、重复客户与改名冲突。待客户管理模块上线后，可在客户档案侧补建/合并；本期**不预留**客户新建弹窗、字段与接口。同名发货人的进一步口径见 Q19。

#### 3.1.5 目的地与路由候选交互

1. 目的地改为**单一输入框**（v1.3）：输入区县/城市关键字（如"白云区"），系统按名称匹配全部可行目的地与路线并列出候选；**同名区县分别展示**，由开单员目视选择。详见 3.1.9。
2. 选中候选后**立即**带出线路；同一目的地的其他路线可在「已选线路」处切换。服务端保存前用区县编码 + 链路指纹二次校验（服务端按 `dest_district_code` 自行取上级编码，避免前端传错）。
3. 候选区（浮层）v1.5 起**每条两行**：第一行为**路由链路**（13px、700 字重、主色 `#365079`，视觉主体，右侧可带「推荐」）；第二行为元信息（12px）：**目的地用橙色 `#b26a1f` 加粗**，后接目的网点、`直达/外转` 标签、节点数、时效、里程。浮层宽 760px、最大高 392px，单条约 54–56px，可完整展示 6 条；展开形态见 3.1.9，选中后收为单行摘要：
   ```
   济南程驰 → 广州 → 白云区 [直达] 3 节点 · 15h · 1,180km   [切换(3)]
   ```
   > v1.11.1：链路文本只保留「节点 → 节点」，末尾不再拼「（直）/（外转）」；类型由右侧徽标表达，避免同一条候选里文字与徽标重复。存储 `route_name` 快照不变，展示层统一剥离。
   > v1.11.2：选中后的线路摘要**只保留一行**，删除原第二行「目的地：… · 目的网点：…」；省市区由目的地输入框与所在地区展示，目的网点由基本信息标题行右侧展示，不再在线路框重复。链路超长时省略号 + hover tooltip，节点数/时效/里程与徽标始终同行。
4. 点击「切换(3)」展开该目的地的路线候选（单选），切换后该条成为当前选择。
5. 候选 > 1 时默认选中排序第 1 条；用户手动切换后，若目的地未变，保持用户选择；目的地变更则重新匹配并回到推荐条，同时提示"目的地已变更，路由已重新匹配"。
6. 无候选时：
   - 物理链路不存在："未找到从当前网点到该目的地的路由，请检查短驳/干线配置"；
   - 有物理链路但无授权外转/直达："当前公司未授权到该目的地的路由，请联系总部授权或新增路由"。
   两种情况都**阻断保存**，不允许无路由落单。
7. 加载中显示骨架条，不允许在加载完成前保存。

#### 3.1.6 费用与支付交互

**费用项（v1.6 三列四行、无分组标题）**：费用项卡片内是一个 `3 列 × 4 行` 网格，按行优先排列；每格「标签在左（54px 右对齐）+ 输入在右」，页面中不再出现「运费组成 / 杂费 / 运费回扣」任何分组小标题。

| 行 | 第 1 列 | 第 2 列 | 第 3 列 |
|---|---|---|---|
| 1 | 运费（右侧标准占位） | 现返 | 欠返 |
| 2 | 送货费（右侧标准占位） | **声明价值** | 保费 |
| 3 | 提货费（右侧标准占位） | 其他费 | 回单费 |
| 4 | 制单费 | — | — |

- 实测（1600×900，CDP `getBoundingClientRect`）：三列 left = **233 / 455 / 678**，四行 top = **541 / 572 / 603 / 634**；格高 26px、行距 31px；每格标签与输入框同处一行（标签 top 548、输入 top 542，差 6px 为行内垂直居中），证明是**按行列排布而非竖排堆叠**。1440×900 下三列 left = 233 / 429 / 625，四行 top 不变。
- 输入宽：带「标准」的运费/送货费/提货费为 100px（输入与标准占位同一行），其余格 148px；1440×900 下分别为 74px / 122px，仍可读。
- 「标准」副字段（Q22，v1.10 已定）：运费、送货费、提货费三格右侧各有一个虚线小标签 `标准 —`，10.5px 灰字，**只展示参考标准价，不参与运费合计、有效运费与任何校验**；本期不接任何数据源、固定占位 `—`，后续若接价目表再单独排期。
- 声明价值（v1.6 新增，第 2 行第 2 列）：即货物保价金额（家伟原话"生命价值"按声明价值处理），金额两位小数、≥0、默认 0.00；**只记录与展示，不计入运费合计，也不参与返款合计/有效运费与四项支付金额分摊**。
- 声明价值与保费的关系（Q21，v1.10 已定）：保费是费用项之一（计入运费合计），声明价值是保价标的金额，两者语义不同。行业常见做法是 `保费 = 声明价值 × 费率`（费率随货物类型/线路/客户协议浮动），但**本期保费独立手填，不做自动计算**；后续扩展点为费率表与计费规则配置，建好后再切换为"按声明价值自动试算保费、允许手工覆盖"，本期不实现费率。
- 运费合计固定在费用项分区标题右侧，返款合计/有效运费在卡底，口径不变：运费合计 = 运费+送货费+提货费+其他费+回单费+制单费+保费（7 项）；返款合计 = 现返+欠返；有效运费 = 运费合计 − 返款合计。
- 支付与配送右卡：支付方式五选一（**v1.5 起无默认值**，未选时整块浅红框 + 占位"请选择支付方式"）；单笔付对应的金额行只读=运费合计；多笔付展开四项；送货方式整块强调；是否回单+数量、是否等通知+备注各一行。
- 代收货款**只留在增值服务·代收款**，费用项不再镜像，避免两处输入口径混淆。

- 支付方式切换、多笔付录入、差额提示的完整规则见第 5 章。
- 运费合计始终只读，实时随 7 个费用项变化；右侧四种支付金额按支付方式自动填充或解锁。
- 返款合计 = 现返 + 欠返，随两个输入实时重算；有效运费 = 运费合计 − 返款合计，紧随其下只读展示。两者均不参与支付四项的金额分配——支付金额仍以**运费合计**为基准（家伟口径：支付分摊对象是运费合计）。
- 有效运费为负时数字变红并追加"（负值）"，保存仍放行但成功提示中注明"按待确认口径放行"；最终是否允许见 Q17。
- 多笔付差额提示条位于四个金额下方，占一整行：
  - 平衡：`四项合计 ¥1,200.00，与运费合计一致`（成功语义色浅底）；
  - 不平衡：`四项合计 ¥1,100.00，运费合计 ¥1,200.00，差额 ¥100.00 未分配`（警告语义色浅底 + 左侧 3px 竖条），保存按钮可点但提交时拦截并聚焦差额。
- 代收货款独立于运费合计；大于 0 时展开收款人/银行名称/银行卡号三项（条件必填，见 Q14）。

**必填可视化（v1.5）**：所有必填字段在未填时统一"红星 + 浅红底"，填入即恢复；支付方式、送货方式额外做整块外框强调。具体状态色：

| 状态 | 背景 | 边框/描边 | 适用 |
|---|---|---|---|
| 未填（必填） | `#fdf7f5` | `#f0d9d4`（控件 1px；支付/送货整块 5px 外圈） | 所有必填项初始态 |

校验方式（硬性）：
- 提交时一次性收集全部错误，合并展示在表单顶部提示条 + 各字段行内提示，**禁止逐个 toast**。

- 数值精度：金额 2 位小数，重量/体积 3 位小数；前端用整数分/整数克运算，避免浮点误差。

#### 3.1.9 保存与并发生效

- 保存成功返回运单号，页面提示"运单 YD20261123000123 已生成"，并提供「查看运单」「继续开单」两个动作。
- **Tab2 确认揽收**：保存动作即"确认揽收"，成功后在同一事务内：① 生成运单（来源 `pre_order_no`）② 预开单 `status=30 已揽收` ③ 回写 `waybill_no` ④ 清空接单草稿。成功后表单区收起、列表刷新，不自动切 Tab。
- 「保存并继续开单」保留开单网点、业务员、支付方式等上下文，清空单据字段（仅 Tab1）。
- 服务端在保存时**重新执行一次路由匹配**并与前端提交的链路指纹（按顺序的 `route_scope + route_id` 列表）比对；不一致返回 409 与"路由已变更，请重新选择"，防止前端用过期链路落单。
- **开单网点以服务端当前机构为准（v1.15）**：客户端传入的 `originDeptId` 被忽略，不因机构切换返回 409；保存归属始终为请求到达时的当前机构。
- 若预开单已被他人接单/已揽收/已撤单，返回 409"预开单状态已变化，请刷新列表"，并附带当前状态，不生成运单（详见 3.3.5）。

#### 3.1.10 目的地单输入与同名区划（v1.5 两行候选）

**输入触发方式**

- 主体输入框只接受区县/城市/省份关键字，输入后 **250ms 防抖**自动检索；按 `Enter` 立即检索（不等待防抖）；右侧「清空」按钮一键清空。
- 不设独立"搜索"按钮：目的地是开单第一步，多一次点击不划算；防抖 250ms 足以覆盖正常输入节奏，回车给熟练开单员一条快速通道。
- 输入为空即清空选择；**输入值一旦被修改，当前已选目的地与线路立即作废**（防止"框里写着 A、落库却是 B"），需要重新从候选选择。

**匹配与展示**

- 匹配范围：全部启用目的地（省 + 市 + 区县名称包含关键字），不区分大小写；本期不做拼音与编码检索（见 Q18）。
- 候选以「目的地 × 路线」展开：同一区县有多条可行路线就出多条；同名区县（如广东省广州市白云区 / 贵州省贵阳市白云区）作为不同目的地**分别列出**，绝不合并。
- 每条候选固定**两行**：第一行只放 `完整链路`（13px / 700 字重 / 主色 `#365079`，右侧「推荐」）；第二行放 `省 市 区县`（12px / 600 字重 / 橙色 `#b26a1f`）+ 目的网点 + `直达/外转` 标签 + 节点数 + 时效 + 里程。这样链路成为视觉主体，目的地用颜色区分，避免上一版"目的地加粗、链路弱化"导致同名区划看不清路线。
- 排序：**节点数升序 → 直达优先于外转 → 时效升序 → 里程升序**（沿用 6.3 的开单匹配排序，并补充两个稳定次级排序，保证同名区县之间也有确定顺序）。
- 候选上限 12 条，浮层宽 760px、最大高 392px；单条约 54–56px，**至少完整展示 6 条**后再滚动，不因两行而只看到两三条。

**多解与无解**

- 多解：全部列出，由开单员选择；不自动替他决定"同名区划选哪个"。选中后仍可在「已选线路」处切换同目的地的其他路线。
- 同名歧义演示数据：搜「白云」返回 **6 条**——广州白云区（直达 3 节点 15h / 直达 4 节点 18.5h / 外转 4 节点 26h）、贵阳白云区（直达 4 节点 32h / 外转 4 节点 38h / 经长沙外转 5 节点 41h），目的网点分别为「广州白云网点」「贵阳白云网点」。
- 弹层实测（1600×900）：单条高 56px，弹层总高 340px、可视区 338px，6 条全部完整可见，无内部滚动；第一行 `font-weight 700 / #365079 / 13px`，第二行目的地 `600 / #b26a1f / 12px`，主次与颜色对比成立。
- 无匹配：浮层显示"未找到匹配的目的地"；若区县存在但无任何可行链路，显示"该目的地暂无可用路由"并列出区县全名与联系方式，保存被阻断（与 6.4 无解口径一致）。

**选中后的回显**

- 输入框回显 `市+区县`（如 `广州市白云区`），避免只留"白云区"再次歧义；「已选线路」固定**单行**：`完整链路 + 直达/外转 + 节点数/时效/里程 + 切换(n)`，链路超长用省略号截断、hover 显示完整链路。v1.11.2 起不再显示第二行「目的地：… · 目的网点：…」辅助文本——省市区由目的地输入框与所在地区展示，目的网点由基本信息标题行展示。
- 省/市/区县不作为独立下拉出现，但会以只读文本随线路显示；落库时由系统带出三级 `code + name` 与 `dest_name`。
- 清空：输入框清空 → 已选线路、省/市/区县、路由全部清空，目的地控件恢复"必填未填写"浅红底；其他已录字段不受影响。

**表结构存法（结论）**

沿用 v1.0 的 4 字段存储，不新增字段：

| 存储 | 字段 | 说明 |
|---|---|---|
| 区划编码 | `dest_province_code` / `dest_city_code` / `dest_district_code` | **唯一判定依据**，来自选中候选；同名区县靠 `dest_district_code` 区分 |
| 区划名称快照 | `dest_province_name` / `dest_city_name` / `dest_district_name` | 落库时快照，区划改名不影响历史展示 |
| 展示全路径 | `dest_name` | 省+市+区县拼接，列表/导出/详情直接用 |
| 线路结果 | `route_name` + `biz_waybill_route_node` | 选中候选的链路摘要与逐段节点快照 |

理由：只存 `district_code` 仍需 join 区划表才能出名称，历史单据会随区划改名而变化；只存名称又无法做同名区划区分与统计。编码 + 名称快照 + 全路径三者并存，是列表筛选（省/市/区县）、路由追溯、导出与对账都能自洽的最小集合。运单列表继续保留「目的地 / 目的地省 / 目的市 / 目的地区县」四列（省/市/区县默认隐藏、可勾选，见 4.2），不受开单交互变化影响。

- 状态标签配色：待接单=警告黄、已接单=信息蓝、已揽收=成功绿、已撤单=危险红（与运单状态标签同一套组件）。
- 列表只显示**当前数据权限范围内**的预开单（见 10.6）；默认筛选项不预置状态，待接单排在最前靠排序与标签区分。

#### 3.3.3 操作列（按状态）

| 状态 | 可用操作 | 说明 |
|---|---|---|
| 10 待接单 | **接单** | 置为 20，写入 `accept_by/accept_time`，打开表单 |
| 20 已接单（本人） | **继续处理**、**退回** | 继续处理=重新打开表单；退回=置回 10，清空接单人 |
| 20 已接单（他人） | 仅显示"×× 处理中"（不可操作） | 点击提示"已被 ×× 接单，重复接单请求将被拒绝（409）" |
| 30 已揽收 | **查看运单** | 提示运单号并跳转运单管理（本期原型只 toast） |
| 90 已撤单 | 无（显示 `--`） | 终态，不可再接单 |

#### 3.3.4 接单带出、锁定与补录

接单后由 `fillPreOrderForm()` 回填，字段处置如下：

| 分组 | 字段 | 接单后 |
|---|---|---|
| 客户 | 客户名称、客户电话 | 由发货人自动匹配带出，**只读展示**；未命中留空；改发货人/电话后自动重算 |
| 发货方 | 发货人、发货电话、发货单位、发货地址 | 带出，可补录/修正 |
| 收货方 | 收货人、收货电话、收货单位、收货地址、省/市/区县 | 带出，可补录/修正；省市区县由申报带出 |
| 目的地 | 省/市/区县、目的地、线路 | 带出并自动重算路由候选，**可改**（改后路由重新匹配） |
| 货物 | 货物名称、件数、体积、重量 | 带出为首行；支持继续加行；类型/包装/备注留空由开单员补（v1.8 不再带数量/单价） |
| 费用 | 全部费用项、现返/欠返 | **不预填**（客户预开单不含价格），从 0 开始录入；返款合计/有效运费随之派生 |
| 支付 | 支付方式、四项金额、代收货款 | 支付方式必选、**无默认值**；四项金额由开单员按实际收款方式录入 |
| 其他 | 送货方式、是否回单、回单数量、是否等通知、备注 | 默认值，可改 |
| 上下文 | 预开单号、提交时间、期望提货时间 | 来源条只读展示 |
| 系统 | 开单员、开单时间、运单号 | 开单员=当前登录人；开单时间=确认揽收时的服务器时间；运单号=确认揽收后生成 |

- 锁定字段用浅灰底 + `readonly`，并加 `title` 说明来源；不可通过前端改值，后端同样以预开单记录为准，忽略请求体中的客户字段。
- 接单动作**只锁定不占用表单**：接单后若切换到 Tab1，Tab2 的接单草稿保留；返回 Tab2 时恢复（见 3.1.1）。
- 退回预开单：二次确认后置回 10、清空接单人、关闭表单；已补录内容丢弃（不落库），因为预开单未生成运单。

#### 3.3.5 重复接单与并发

- **接单**采用乐观锁：`UPDATE biz_pre_waybill SET status=20, accept_by=?, accept_time=?, version=version+1 WHERE id=? AND status=10 AND version=?`；影响行数=0 时返回 `409`，前端提示"该预开单已被他人接单，已为你刷新列表"，并自动刷新。
- **确认揽收**同样带 `version` 与 `status=20` 条件：只有接单人（或管理员代操作）能确认；状态已变则 409，不生成运单。
- 同一预开单只允许存在一条有效运单：`biz_waybill.pre_order_no` 建**唯一索引**（`deleted=0` 场景由应用层保证；见 8.5），重复提交由唯一索引兜底。
- 退回也带 `version`，避免把他人刚确认揽收的单退回。
- 列表 30 秒不自动轮询，避免打断录入；刷新按钮与接单/确认失败后主动刷新。

#### 3.3.6 与运单、客户表的关系

| 关系 | 字段 | 说明 |
|---|---|---|
| 预开单 → 运单 | `biz_pre_waybill.waybill_no` / `biz_waybill.pre_order_no` | 双向可追溯：预开单记录生成的运单号，运单记录来源预开单号 |
| 运单 → 关联单号 | `related_no` | **与预开单号无关**：关联单号仍是客户/上游单据号，手工录入；预开单号单独存 `pre_order_no`，不占用关联单号 |
| 预开单 → 客户 | `biz_pre_waybill.customer_id` + `customer_name/customer_phone` 快照 | 客户端提交时按客户账号绑定客户，作为来源留痕；v1.4 起开单页客户名称以**发货人自动匹配结果**为准，命中则运单写匹配到的 `customer_id` 与快照，未命中留空 |
| 预开单 → 归属机构 | `dept_id` | 取预开单受理网点（客户端按客户归属或收件网点路由），确认揽收后运单 `dept_id` 取**接单网点**（= 当前机构） |

预开单号与运单号是**两套独立编号**：预开单号 `YJ...` 由客户端提交时生成，运单号 `YD...` 由确认揽收时生成；两者都不是关联单号。

### 3.4 子母单设计（v1.9 定稿）

> 定稿结论（家伟确认）：**计费与客户结算挂母单，子单只承担装卸车与节点流转**；编号采用 `母单号-两位序号`。拆分规则、状态汇总、扫码粒度、并发唯一性按本文建议定稿；仍标注「待定」的 Q 项需家伟确认。

#### 3.4.1 编号规则

- **母单号**：`YD + yyyyMMdd + 6 位日内流水`（16 位），沿用 8.1 的运单号规则。
- **子单号**：`母单号-两位序号`，如 `YD20261123000126-01`；序号 1–99，固定两位补零。
- **序号分配**（并发安全）：
  1. 拆单事务内先 `SELECT ... FROM biz_waybill WHERE id=? FOR UPDATE` 锁母单行；
  2. `SELECT COALESCE(MAX(child_seq),0)+1 FROM biz_waybill WHERE parent_id=? AND deleted=0` 取下一个序号；
  3. 插入子单，由 `uk_parent_child(parent_id, child_seq)` 兜底；唯一冲突（1062）时回滚并重试，最多 3 次，仍失败返回 `409 拆单并发冲突，请重试`；
  4. 序号**不回收**：子单撤销后序号留空，后续拆单继续递增，保证历史单号可追溯。
- **唯一索引**：
  - `uk_waybill_no(waybill_no)`：母子单号全平台唯一（子单号本身也是运单号）；
  - `uk_parent_child(parent_id, child_seq)`：同一母单下子单序号唯一；母单 `parent_id IS NULL` 不参与该唯一键（MySQL 唯一索引允许多个 NULL）；
  - `idx_parent_no(parent_no)`：按母单号查子单。
- 母单号、子单号创建后**不可修改**；子单号不允许超过 99，超过需拆成两张母单或走总部特殊审批。

#### 3.4.2 数据模型

**建议：同一张 `biz_waybill` 表自关联，不建独立子表。**

| 字段 | 类型 | 母单 | 子单 | 说明 |
|---|---|---|---|---|
| `parent_id` | BIGINT UNSIGNED NULL | NULL | 母单 id | 自关联；仅两级，子单不可再拆 |
| `parent_no` | VARCHAR(32) NULL | NULL | 母单号 | 母单号快照，便于按母单号查询/打印，避免每次 join |
| `is_child` | TINYINT(1) NOT NULL DEFAULT 0 | 0 | 1 | 单据类型标识；列表徽标与筛选依据 |
| `child_seq` | SMALLINT UNSIGNED NULL | NULL | 1–99 | 子单序号；与 `parent_id` 联合唯一 |

**为什么用同表自关联：**
- 母单、子单共享收发方、货物、路由、状态、数据权限、审计等 50+ 字段；独立子表会造成字段双份、列表/详情/导出/权限全量双写。
- 子单本身就是运单：要独立装车、走不同路由、产生节点、打印标签、参与数据权限；放同表可直接复用现有运单列表、详情、导出与权限体系。
- 只需要两级（一票多车），自关联足够；未来若出现三级转运，再引入独立 `biz_waybill_relation` 表，不提前设计。

**约束：**
- 子单的父单必须是 `is_child=0` 的母单；子单不可再拆（应用层校验）。
- 母单存在有效子单时，件数/重量/体积为**只读汇总值**；拆分/合并时校验 `母单 = Σ有效子单`，重量/体积误差 < 0.001。
- 母单与子单的省/市/区县、目的地必须一致；子单可走不同路由、不同车辆（见 3.4.5）。
- 子单费用字段固定为 0，不参与客户结算（见 3.4.4）。

#### 3.4.3 拆分规则

| 规则 | 定稿内容 |
|---|---|
| 产生时机 | **两种都支持**：开单时按需直接拆；装车时也可拆（同一母单内换车）。默认开单不拆（一票一车），只有明确"一票多车"才拆 |
| 拆分入口 | 开单页货物区「拆单」、运单详情「拆分子单」、装车扫码页「拆单装车」 |
| 拆分参数 | 每张子单的件数、重量、体积（默认按件数比例带出，可改）、路由、车辆（可空，装车时再指定） |
| 数量约束 | 至少 1 张、最多 99 张；每张件数/重量/体积均 > 0；合计必须等于母单；目的地必须一致 |
| 合并 | 仅**未装车**（所有子单 status ≤ 20）可合并；合并后子单置 `90 已作废`，合并动作写 `biz_waybill_log`（`action_type=2`，原因可空，前后快照必填），母单恢复未拆；已产生装车/节点记录不可合并 |
| 撤销 | 未装车前可撤销单张子单；撤销后剩余子单合计仍须等于母单，否则需先补拆；全部撤销后母单回到未拆 |
| 母单作废 | 存在有效子单时禁止作废，必须先撤销/作废全部子单 |
| 改挂 | 子单不可改挂其他母单；需要改挂时撤销后重拆，保留原单审计 |
| 审计 | 拆、合、撤、作废、强制签收均写 `biz_waybill_log`（操作人、时间、前后快照 `waybill+children[]`）；**撤销拆单/作废/强制签收必填原因，拆单/合单原因可空**（7.6） |

#### 3.4.4 费用与结算（定稿）

- **所有费用项、声明价值、现返/欠返、四项支付金额、代收货款、客户对账、开票与返款全部挂母单**。
- 子单费用字段（运费/送货费/提货费/其他费/回单费/制单费/保费/现返/欠返/四项支付/代收/声明价值）固定为 0；开单页与详情页对子单**隐藏费用录入**，显示"费用挂母单"。
- 子单不生成应收、不参与客户结算；子单撤销/合并不影响母单费用。
- **成本分摊本期不做，仅预留扩展**：未来若需核算多车成本，新增 `biz_waybill_cost_alloc`（子单 id、成本类型、金额、承运商、结算单号）或子单 `carrier_cost` 字段，按重量/体积/件数比例分摊，合计必须等于母单成本；只用于内部成本，不参与客户结算。接口预留 `GET/POST /api/waybill/{no}/cost-alloc`，本期不实现。

#### 3.4.5 路由与流转

- **子单可独立路由、独立车辆、独立承运商**；母单的 `route_name` 是开单时的商业路由摘要，拆单后仅作参考，实际运输以子单路由为准。
- **状态码补充**：`25 已拆单`、`55 部分到达`、`70 异常`；保留 10 待揽收 / 20 已揽收 / 30 已装车 / 40 运输中 / 50 已到达 / 60 已签收 / 90 已作废。
- 子单状态：10 → 20 → 30 → 40 → 50 → 60；异常 70；作废 90。
- **母单状态由子单汇总**（不允许在详情页手工推进，作废除外）：

| 母单状态 | 触发条件 |
|---|---|
| 25 已拆单 | 已拆出子单、尚无子单装车 |
| 30 已装车 | 全部有效子单均已装车 |
| 40 运输中 | 任一有效子单处于运输中 |
| 55 部分到达 | 部分有效子单到达/签收，未全部到达 |
| 60 已签收 | **全部有效子单均已签收，或经 `force-sign` 强制签收（Q28）** |
| 70 异常 | 任一有效子单异常且未解除 |

- 子单状态变更后调用 `recalcMotherStatus(parentId)` 重算母单；正常情况下母单 60 需要所有有效子单 60，部分到达只到 55；**强制签收是唯一例外**（Q28），不因汇总规则被立即回退。
- **强制签收（Q28 已定）**：母单处于 50 已到达或 55 部分到达时可操作；需 `operation:waybill:force-sign` 权限并必填原因；操作后母单置 60，**子单状态不回写**、未到子单继续按各自节点流转；动作、操作人、原因、时间写 `biz_waybill_log`（见 7.6，`action_type=5`）；不新增运单字段、不改变 58 项口径。
- 节点记录 `biz_waybill_route_node.waybill_id` 存**子单 id**；母单时间轴按子单聚合展示，节点标注子单号。
- 异常：子单 70 时母单 70；异常解除后按汇总重算。

#### 3.4.6 打印与扫码

- **装车扫码：扫子单**。扫母单时拒绝并提示"母单不可装车，请扫子单 -01/-02"；子单校验 status ∈ (20,25)、车辆匹配、目的地一致。
- **到达/签收：扫子单**；POD 按子单记录；母单在全子单签收后自动置 60，也可在 50/55 时经强制签收置 60（Q28）。
- **标签张数**：母单 1 张（客户/结算联）+ 每张子单 1 张；重打需记录操作人与次数。
- **子单标签内容**：子单号（最大字号）、母单号、序号 n/N、件数/重量/体积、目的地/目的网点、收货人、末段路由、车辆（可空）、二维码（子单号）、"子单"标识；**收货人电话不打印**（Q27 口径，模板后续单独定）。
- **母单标签内容**：母单号、总件数/重量/体积、客户名称、目的地、子单数量、"母单·禁止装车"标识、二维码（母单号）。
- 二维码内容即单号本身，不新增条码字段。
- **链路文本口径（v1.11.1）**：标签上的链路/末段路由只写「节点 → 节点」，不带「（直）/（外转）」后缀；直达/外转由标签上的徽标或单据 `route_end_type` 表达，避免同一位置重复。

#### 3.4.7 字段清单与列表影响

- 新增 4 个字段：`parent_id`（技术字段，不出列）、`parent_no`、`is_child`、`child_seq`。
- 字段总数 **52 → 56**（46 手工 + 4 支付派生 + 2 返款派生 + 4 子母单管控），v1.11 再增至 **58**（+2 网点派生，见 3.5/4.0）；若沿用 v1.8 的 49 口径则需先确认（见 4.0）。
- 列表列池（v1.11.5 现状）：**单据类型**（默认隐藏）、**子单序号**（默认隐藏）保留；`parent_no` 字段仍落库但**不再作为列表列出**（母单恒为空，属于空列）；列池 57→**56**、默认 19→**18**、隐藏仍 **38**（56−18；原文误写 37，v1.13 修正）。
- **列表只显示母单（v1.11.3，v1.11.4 入口修正，v1.11.5 列调整）**：只渲染 `is_child=0` 的行，子单不作为独立行；**运单号列的母单号本身作为入口**——有子单时点击直接弹子单清单（子单号/件数/重量/体积/始发网点/运达网点/状态），无子单时点击进入运单详情；关闭后可再点其他母单号切换。运单号文本保持完整，**"母"徽标后置**在单号之后，仅该运单有子单时出现；无子单不加任何标识；删除母单号列。
- **合计只按母单（v1.11.3）**：合计行只累加列表中的母单，避免母单与子单重复累加；当前演示数据为 **1,555 件 / 24,895.000 kg / 126.200 m³**（26 张母单）。
- **网点与子母单（v1.11）**：母单与子单都各自落 `origin_hub_id/origin_hub_name`、`dest_hub_id/dest_hub_name`。拆单时子单网点**随子单路由带出**：始发网点默认继承母单始发网点（同一揽收网点），运达网点按子单路由终点确定；**子单运达网点可以与母单不同**（一票多车可能分送不同末端网点），但**所有子单的目的地区县必须与母单一致**，且子单运达网点必须属于该目的地区划，禁止跨目的地拆单。母单列表展示母单自己的网点；查看子单时展示子单网点。
- 导出：**只导出当前筛选后的母单**，行数 = 母单条数，不含子单行；随当前可见列，**列清单不含母单号**，运单号导出**纯单号**（无"母"徽标等装饰），网点导名称快照。
- 详情：母单展示**子单清单**与"母单合计 = 子单合计"对比；子单展示母单号、子单序号与"费用挂母单"提示；子单清单增加「运达网点」一列，便于核对是否与母单一致。
- 筛选：列表只显示母单；母单号列已删除（v1.11.5），不再提供该列筛选；单据类型/子单序号列默认隐藏，如勾选仍可按需过滤；网点为下拉单选（见 3.5）。

- 本期只定义契约，不实现接口。

### 3.5 始发网点 / 运达网点（v1.11）

家伟新增两个字段，字段总数 56 → 58。二者都是**随路由自动带出的只读派生值**，开单员不手工填写，避免"网点与地址不一致"。

#### 3.5.1 取值规则

| 字段 | 列名（id + 名称快照） | 取值来源 | 展示 |
|---|---|---|---|
| **始发网点** | `origin_hub_id` + `origin_hub_name` | 取所选路由的**首节点出发网点**；正常场景即当前机构（开单网点）。开单网点本身固定取当前机构、只读不可选（v1.15） | 开单页进入即显示当前机构；正常场景不会为空 |
| **运达网点** | `dest_hub_id` + `dest_hub_name` | **v1.15 运达网点派生优先级**：① 末段目标网点本身是网点（有归属机构，`dept_type=5` 且启用）→ 取该网点；② 末段只到区划、无归属网点（外转/直达到区划）→ **回落为始发网点**（同一单的 `origin_hub`）；③ 任何情况下都**不得取路由中间的分拨中心或与始发无关的节点**。切换路由时同步刷新 | 如"济南分拨中心 → 白云区"外转直达，运达网点 = 始发网点，不再错误显示"济南分拨中心"；末段到真实网点（如广州白云网点）时取该网点 |

- 为什么存 id + 名称快照：id 用于归属统计与权限，名称快照用于列表/导出/打印，网点改名不影响历史单据；与目的地"code + name"口径一致。
- 为什么只读：网点是路由结果，不是可独立录入口；若允许手填，会出现"地址到 A 区、网点写 B 网点"的不一致，运达网点还会影响末端派送归属。**Q29 已定：本期只读，不开放人工修改入口。**
- 表单联动：`选择目的地 → 匹配候选路由 → 选中一条 → 始发/运达网点同时刷新`；切换线路同步刷新。保存时服务端按 `route_name` + 目的地编码重新校验，前端值不作为可信来源。

#### 3.5.2 开单页展示位置

- 放在**基本信息分区标题行右侧**，两枚只读标签：`始发网点 济南程驰`、`运达网点 —`，13px 灰标签 + 主色值，与分区标题同一行，**不占字段网格、不增加一屏高度**。
- 纯文本、无输入框、无下拉、无清除按钮；不设红星、不参与必填校验。
- 移动端/窄屏（<1320px）随分区标题折行到下一行，不影响一屏承诺。

#### 3.5.3 列表、筛选与导出

| 项 | 方案 | 理由 |
|---|---|---|
| 列池 | +2 列：`originHubName`「始发网点」、`destHubName`「运达网点」；列池 54 → **56** | 两个字段都可查 |
| 默认显示 | **运达网点默认显示**，放在「目的地」之后；**始发网点默认隐藏**，列设置可勾选 | 运达网点=派送归属，是列表最常看的"货交给哪个网点"；始发网点绝大多数等于开单网点，与"开单网点"列信息重叠，默认隐藏避免多一列噪音；需要跨网点揽收统计时再勾选 |
| 默认列数 | 17 → **18**；隐藏 37 → **38** | 只多一列，列表宽度仍可控 |
| 筛选形态 | **下拉单选**（选项为启用的网点名称） | 网点是有限枚举，按单网点查询是主场景，单选交互更轻；与前端规范"下拉默认多选"的差异在此显式声明。Q29 已定本期单选，后续如出现"多网点对比"需求另立变更 |

#### 3.5.4 详情抽屉

- 基本信息区增加两项只读：`始发网点`、`运达网点`，展示名称快照；鼠标悬浮显示网点 id 与编码（便于排查）。
- 路由链路时间轴的**首节点**与**终点节点**高亮，并与两个网点字段对应；若历史单据的路由配置已变更，以运单快照为准，不重新解析。
- 子单详情展示子单自己的网点；母单详情的子单清单增加「运达网点」列。

#### 3.5.5 子母单场景

- 母单、子单都落自己的网点字段；**子单始发网点默认继承母单**（同一揽收网点拆车），**子单运达网点随子单路由终点带出，可与母单不同**。
- 允许不同的原因：一票多车可能分送同一区县的不同末端网点，各子单按自己的路由终点落网点；强行要求一致会迫使拆单前先改母单路由。
- 约束：**所有子单的目的地区县必须与母单一致**；子单运达网点必须属于该目的地区划；拆单接口校验，不一致返回 409。母单的 `dest_hub_name` 记录开单时路由终点，拆单后仅作参考，实际派送以子单网点为准（与 3.4.5 "实际运输以子单路由为准"一致）。

#### 3.5.6 Q29（v1.12 已定）

**结论：始发网点、运达网点一律只读，由路由派生，不允许人工修改。** 前端不出现编辑入口，后端保存时按 `route_name` + 目的地编码重算并覆盖客户端传值。若未来业务确需变更网点，应另立路由变更需求，不在本期开单与运单字段中预留编辑能力。筛选形态本期为下拉单选。

### 4.0 口径说明

- **58 项**按家伟原话逐项落库（46 个手工录入 + 4 个支付派生 + 2 个返款派生 + 4 个子母单管控 + 2 个网点派生），字段名使用后端下划线、前端驼峰。

## 5. 金额与支付校验规则

### 5.1 金额定义

设七个费用项、两个返款项与一个声明价值：

```
F = { freight_fee 运费, delivery_fee 送货费, pickup_fee 提货费, other_fee 其他费,
      receipt_fee 回单费, make_bill_fee 制单费, insurance_fee 保费 }
B = { cash_back 现返, owe_back 欠返 }
D = { declared_value 声明价值 }        （v1.6，单列记录，不属于 F）

运费合计   total_fee     = ΣF
返款合计   rebate_total  = cash_back + owe_back          （v1.2）
有效运费   valid_freight = total_fee − rebate_total       （v1.2，可为负，见 Q17）

支付金额 = { prepaid_fee 现付运费, collect_fee 到付运费,
             monthly_fee 月结运费, return_fee 回付运费 }
```

口径：
- 所有金额 `DECIMAL(12,2)`、两位小数，舍入方式 `HALF_UP`。
- `现返 cash_back`、`欠返 owe_back` 为**非负**录入（≥0）；它们**不参与**运费合计，也不参与四种支付金额的分摊，但通过 `返款合计` 影响 `有效运费`。
- **支付金额的分摊基准是运费合计 `total_fee`，不是有效运费**——家伟口径：现付/到付/月结/回付/多笔付四项之和必须等于运费合计。返款是给客户的让利，不改变应收的运费结构。
- `声明价值 declared_value`（v1.6）是货物保价金额，**不属于 F**，不计入运费合计、返款合计、有效运费与四项支付金额；保费 `insurance_fee` 仍作为费用项手工录入并计入 F，二者关系与费率来源见 Q21。
- `代收货款 cod_amount` 独立于运费合计，不参与支付分摊，也不参与返款合计/有效运费。
- 运费合计允许为 0（例如免费/内部单），但费用项与返款项不能为负。
- `rebate_total`、`valid_freight` 由服务端计算并落库，客户端传值一律忽略（与 total_fee、四项支付金额一致）。

### 5.2 支付方式与四项金额的映射（硬性）

| 支付方式 | prepaid_fee | collect_fee | monthly_fee | return_fee | 校验 |
|---|---|---|---|---|---|
| 1 现付 | = total_fee | 0.00 | 0.00 | 0.00 | 服务端强制覆盖 |
| 2 到付 | 0.00 | = total_fee | 0.00 | 0.00 | 服务端强制覆盖 |
| 3 月结 | 0.00 | 0.00 | = total_fee | 0.00 | 服务端强制覆盖 |
| 4 回付 | 0.00 | 0.00 | 0.00 | = total_fee | 服务端强制覆盖 |
| 5 多笔付 | 可录入 ≥0 | 可录入 ≥0 | 可录入 ≥0 | 可录入 ≥0 | 四项之和必须等于 total_fee |

**"0 还是空"的结论：0，不是 NULL。** 理由：
1. 四列是 `NOT NULL DEFAULT 0`，避免 `NULL` 参与 `SUM/AVG`、排序、区间筛选时出现口径分叉；
2. 列表与详情展示 `0.00` 比空更明确，用户能看出"该项不适用"而不是"忘记填"；
3. 多笔付求和时无需 `COALESCE`，前后端口径一致；
4. 前端对非适用项显示 `0.00` 且禁用（灰色），不是隐藏，避免用户误以为字段消失。

### 5.3 前端联动规则

| 场景 | 行为 |
|---|---|
| 单笔付（1-4）下修改任一费用项 | 运费合计实时重算；对应支付金额自动同步为新的合计；其余三项保持 0.00 |
| 从单笔付切到另一种单笔付 | 原对应项归 0.00，新对应项 = 合计；无需二次确认 |
| 从单笔付切到多笔付 | 四项全部解锁，默认保留原对应项金额，其余为 0.00；立即显示差额；差额≠0 时保存被拦截 |
| 从多笔付切到单笔付 | 二次确认"将清空已录入的多笔付金额"，确认后按新方式覆盖 |
| 多笔付下修改费用项 | 合计变化，已填四项**不自动改**；差额条实时更新，保存拦截直到平衡（不自动平摊，见 Q7） |
| 多笔付下修改某一项金额 | 只重算四项合计与差额，不改其他三项 |
| 现返/欠返变化 | 不影响运费合计、四项合计与差额；实时重算「返款合计」与「有效运费」；有效运费为负时数字变红并追加"（负值）" |
| 代收货款变化 | 不影响运费合计；>0 时展开并校验收款人/银行/卡号 |

差额展示：
- 平衡：成功语义色浅底条，文案 `四项合计 ¥1,200.00，与运费合计一致`；
- 不平衡：警告语义色浅底条 + 3px 左侧竖条，文案 `四项合计 ¥1,100.00，运费合计 ¥1,200.00，差额 ¥100.00 未分配`；
- 不使用亮红/亮绿；金额两位小数千分位。

### 5.4 后端强制约束（不可只靠前端）

保存事务内按以下顺序执行：

1. 按七个费用项重新计算 `total_fee`，**忽略客户端传入的 total_fee**；
2. 按 `cash_back + owe_back` 计算 `rebate_total`，再按 `total_fee − rebate_total` 计算 `valid_freight`，两个结果**强制覆盖**客户端传值；校验 `cash_back ≥ 0`、`owe_back ≥ 0`；
3. 按 `pay_method` 重新计算四项支付金额：
   - 支付方式 1-4：对应项 = total_fee，其余三项强制写 0；
   - 支付方式 5（多笔付）：读取客户端四项，校验每项 ≥0 且 `prepaid + collect + monthly + return == total_fee`（按分比较，不用浮点）；
4. 任一不满足返回 `400`，错误结构包含字段名与文案，例如：
   - `支付方式为多笔付时，现付/到付/月结/回付四项合计必须等于运费合计，当前差额 100.00`
   - `支付方式为现付时，仅现付运费可等于运费合计，其余三项必须为 0`
5. 金额精度：服务端使用 `BigDecimal`，`setScale(2, RoundingMode.HALF_UP)`；禁止 `double`；
6. 数据库层不加 `CHECK` 约束（避免后续口径调整需要改表），由服务端与单元测试保证；派生金额只允许由 `WaybillAmountCalculator` 一处计算，禁止在 Controller/前端或 Mapper 中二次拼算；
7. 更新运单时同样重算与重校验，不允许只改四项金额或返款项绕过合计；
8. **必填数值校验（v1.14/R1）**：运单 `quantity>=1`、`weight>0`、`volume>0`；预开单 `quantity>=1`、`weight>0`，`volume` 未申报按 0 落库、申报则必须 >0；不满足返回 `400`，不得依赖数据库默认值兜底。
9. **运费 / 送货费必填（v1.15）**：`freight_fee` 必须显式传值且 `>=0`（允许 0），留空（null）返回 `400`「运费不能为空」；当 `delivery_method ∈ {1 送货, 3 大车直送}` 时 `delivery_fee` 必须显式传值且 `>=0`（允许 0），留空返回 `400`「送货方式为送货或大车直送时，送货费不能为空」；`delivery_method=2 自提` 不要求；`delivery_method` 为空时只返回「请选择送货方式」，不叠加送货费报错。前端仅做同步提示，最终以后端校验为准。
10. **开单网点（v1.15）**：`originDeptId` 一律以账号当前机构（顶部机构切换后的机构，即数据权限锚点）为准，**忽略客户端传值**；当前机构不存在或已停用返回 `400/403`。保存归属 `dept_id` = 当前机构。

### 5.5 边界与异常

- 多笔付四项全为 0 且合计=0：允许（免费单）。
- 多笔付某一项为负：拒绝。
- 单笔付客户端回传非对应项非 0：服务端静默纠正为 0 并记录 WARN，不返回错误（避免前端旧版本报错），但接口文档注明"以服务端为准"。
- 金额超过 `DECIMAL(12,2)` 上限：`400`，提示"金额超出允许范围"。
- 运费合计为 0 但代收货款 >0：允许，代收与运费独立。
- **有效运费为负**（现返+欠返 > 运费合计）：v1.2 默认口径为**允许保存、不阻断**，前端红色标注并在成功提示中注明"按待确认口径放行"；后端只记录 WARN 日志，不做拒绝。是否改为"阻断/要求审批/限制返款上限"由家伟在 Q17 拍板，本期不擅自拦截。

## 6. 路由拼接算法

> 本章定义开单时"目的地 → 路由链路"的可实现算法。算法基于现有 `sys_route`（短驳/干线）与 `sys_route_transfer`（外转/直达）两张表，不新增路由表。
> **排序口径以家伟本轮原话为准：第一排序按节点数量（越少越靠前），第二排序直达优先于外转。** 该口径 **覆盖** `route-region-design-v2.1.md` §2.7.3 的旧排序（旧版为"直达 > 完整链路 > 外转"优先），差异见 6.8。

### 6.1 输入与节点定义

| 项 | 定义 |
|---|---|
| 起点 O | 开单网点，`sys_dept.id`，类型 4/5，`status=1`、`allow_ship=1`，且在开单员当前管理范围内 |
| 终点 R | 目的地区县，`sys_region` 的区县编码（本期三级；乡级见 Q4） |
| 节点 | 机构 ID（网点/分拨中心）；终点区划作为一个特殊节点参与节点计数 |
| 短驳/干线边 E1 | `sys_route`：`origin_dept_id → dest_dept_id`，`status=1`、`deleted=0`，属性含 `route_category(1短驳/2干线)`、`transit_hours`、`mileage`、`warehouse_area` |
| 外转/直达边 E2 | `sys_route_transfer`：`apply_dept_id → region_code`，`status=1`、`deleted=0`，`transfer_type(1直达/2外转)`，按授权过滤 |

链路形态（只允许以下两种）：
1. `O --E2--> R`（起点直接有到目的地区划的外转/直达路由）；
2. `O --E1*--> D --E2--> R`（先走短驳/干线到某个机构 D，再由 D 的外转/直达路由到目的地）。

说明：家伟示例 `济南程驰 → 济南分拨中心 → 广州 → 白云区（直）` 即形态 2：两段 E1 + 一段 E2。链路必须以 E2 结束；终点的"区划"本身作为最后一个节点参与计数。

### 6.2 候选集加载（一次请求内完成）

```
公司 C = 开单员当前机构向上最近的 dept_type=2 公司；若当前机构为总部或路径无公司，则 C=总部
E1 = SELECT * FROM sys_route
     WHERE deleted=0 AND status=1
       AND (owner_company_id = C OR owner_company_id = 1)   -- 见 6.4 / Q3
E2 = SELECT t.* FROM sys_route_transfer t
     WHERE t.deleted=0 AND t.status=1
       AND t.region_code IN (区县编码, 市编码, 省编码)
       AND (
             C = 总部
             OR EXISTS (SELECT 1 FROM sys_route_company rc
                        WHERE rc.route_scope=2 AND rc.route_id=t.id
                          AND rc.company_dept_id IN (C, 0))
           )
```

约束：
- 路由两张表已豁免数据权限行级过滤，**必须像上面这样显式过滤**，不得依赖拦截器。
- 目的地按"区县 → 市 → 省"逐级回退；同一机构 D 若同时命中多级，只取最细一级（区县优先），避免重复候选。
- E1/E2 的机构端点必须 `status=1`、`deleted=0`；`sys_dept` 已豁免，需显式校验。
- 数据量保护：单次加载 E1 上限 5000 条；超过则报错"路由数据量超出匹配上限，请联系管理员"（不静默截断）。

### 6.3 图搜索与候选生成

```
候选 = []
for path in BFS(起点 O, 边 E1, 最大边数=4, 禁止环, 节点数≤5):
    D = path 的末端机构
    for level in [区县, 市, 省]:              # 逐级回退
        for e2 in E2 where e2.apply_dept_id == D and e2.region_code == level.code:
            候选.add(path + e2)
        if 本 level 有命中: break              # 只取最细一级
按 6.5 排序、去重、截断 50 条
```

细节：
- `BFS` 深度按边数计，最多 4 段 E1（节点数 ≤6，含起点和终点区划）；与 v2.1 的"最多 5 跳"一致。
- 去重键：`按顺序拼接的 (route_scope, route_id)`；同一链路只保留一条。
- 截断：先按 6.5 排序，再取前 50 条，保证"先算对再截断"，不是先截断再排序。
- 时间复杂度：E1 为网点间边，量级有限；BFS + 邻接表在内存完成，单次请求毫秒级。
- 服务端不缓存匹配结果（路由/授权随时可变）；如需缓存，key 必须含公司 + 区县 + 路由版本，且变更即失效。

### 6.4 跨公司授权与末端网点共用

| 场景 | 处理 |
|---|---|
| 外转/直达路由授权 | 分公司 C：`sys_route_company` 存在 `company_dept_id=C` 或 `=0`；总部：不做授权过滤 |
| 总部创建的"全部"路由 | `company_dept_id=0` 标记行动态生效，新增分公司自动可用，不展开快照 |
| 分公司创建的独占路由 | 未授权给 C 时不得进入候选；即使用户手工构造请求也会被服务端过滤 |
| 短驳/干线路由 | 无授权概念；按 `owner_company_id ∈ (总部, C)` 参与拼接（Q3）。理由：总部维护网络级物理段，分公司自有物理段只服务本公司；若直接放开"全部启用"，会让 A 公司用到 B 公司私有短驳段 |
| 末端网点多公司共用 | 开单员在共用末端网点开单时，公司 C **取开单员当前机构所属公司**，不取该网点所有适用公司；网点可被 C 选中，仅说明它在 C 的管理范围内（`sys_dept_apply_company` 含 C） |
| 开单员为总部 | C=总部，E2 不做授权过滤；E1 取全部启用（`owner_company_id ∈ (1, 1)` 即全部） |
| 路由停用 | 不参与候选；恢复启用后自动恢复 |
| 路由被取消/逻辑删除 | 不参与候选；已生成的运单快照不受影响 |

### 6.5 排序规则（严格执行）

| 优先级 | 排序键 | 方向 | 说明 |
|---|---|---|---|
| 1 | 节点数量 | 升序 | 节点越少越靠前；节点数 = 链路中机构节点 + 终点区划节点（含起点） |
| 2 | 末段类型 | 直达优先 | `transfer_type=1` 排在 `2` 前；末段是 E2，所以只看最后一段 |
| 3 | 区域匹配深度 | 区县 > 市 > 省 | 同一节点数、同类型时，目的地匹配越精确越靠前 |
| 4 | 总时效 | 升序 | 各段 `transit_hours` 求和；NULL 视为无穷大，排最后 |
| 5 | 总里程 | 升序 | 各段 `mileage` 求和；NULL 视为无穷大 |
| 6 | 末段 `sort_order` | 升序 | 路由管理页配置的排序号 |
| 7 | 末段 `id` | 升序 | 保证结果稳定可复现 |

示例排序：
- A：`O→D1→D2→R`，4 节点，末段直达；
- B：`O→D3→R`，3 节点，末段外转；
- C：`O→D1→D2→R`，4 节点，末段外转。
结果：B（3 节点）→ A（4 节点、直达）→ C（4 节点、外转）。即使 A 是直达，也不能越过节点更少的 B——这是家伟本轮明确的口径。

### 6.6 多解展示与选择

- 接口返回候选数组，每项含：
  ```
  { chainText, nodes:[{deptId,deptName,type}], routeIds:[{scope,id,code,type}],
    nodeCount, endType, totalHours, totalMileage, matchLevel, recommended }
  ```
- 第 1 条 `recommended=true`；前端默认选中并展示"推荐"标记。
- 候选 >1 时显示「切换路由 (N)」；展开后单选，展示链路文本、`直达/外转` 标签、节点数、时效、里程。
- 用户切换后，表单提交所选链路的 `routeIds` 顺序列表；服务端保存时重新匹配并比对（6.7）。
- 候选 =1 时不显示切换入口，只展示链路。
- 候选 =0 时按 6.6.1 阻断。

#### 6.6.1 无解处理

| 情况 | 判定 | 文案 | 动作 |
|---|---|---|---|
| 无物理链路 | BFS 未到达任何有 E2 的机构，且起点也无 E2 | `未找到从当前网点到该目的地的路由，请检查短驳/干线配置` | 阻断保存，保留已填内容 |
| 有链路但未授权 | 存在 E2 但均不满足授权 | `当前公司未授权到该目的地的路由，请联系总部授权或新增路由` | 阻断保存 |
| 目的地未选定 | 仅输入关键字、未从候选选中（或无 `dest_district_code`） | `请从候选列表中选择唯一目的地` | 阻断保存与匹配请求 |
| 路由数据超限 | E1 >5000 条 | `路由数据量超出匹配上限，请联系管理员` | 阻断并记录日志 |

服务端错误码建议：`42201` 无物理链路、`42202` 未授权、`42203` 数据量超限；前端按码展示不同文案。

### 6.7 保存时二次校验与快照

- 保存请求携带：`originDeptId`（服务端以当前机构为准，忽略前端）、目的地三码、所选链路 `routeIds[]`。
- 服务端重新执行 6.2-6.5，找到与 `routeIds[]` 完全一致（顺序、scope、id 均一致）的候选：
  - 找到：事务内写 `biz_waybill` + `biz_waybill_route_node`（每段一行，按 `seq` 排序）；
  - 未找到：返回 `409` `路由已变更，请重新选择`，不写任何数据。
- 快照内容：每段的 `route_scope/route_id/route_code/route_category/transfer_type/from/to/承运商/库区/时效/里程`，以及链路摘要 `route_name`、节点数、末段类型。
- 打印/轨迹后续直接读快照，不重新匹配，避免历史单据随路由配置变化而改变。

### 6.8 与 v2.1 的差异（必须知会）

| 项 | v2.1 §2.7.3 | 本方案（家伟本轮） | 处理 |
|---|---|---|---|
| 第一排序 | 直达 > 完整链路 > 外转 | **节点数量升序** | 以本轮为准，v2.1 该条对开单侧失效 |
| 第二排序 | 目的地匹配深度 | **直达优先于外转** | 以本轮为准 |
| 其余 | 时效、里程、跳数、sort_order、id | 保留，作为第 3-7 位 | 兼容 |
| 短驳/干线可见性 | §4.3 矩阵写"分公司仅授权（含0）" | Tab1 无授权行，按 `owner_company_id ∈ (总部, C)` | 存在冲突，列入 Q3 待裁决 |

### 6.9 示例逐步推演

已知：
- `sys_route`：`501 济南程驰 → 601 济南分拨中心`（短驳），`601 济南分拨中心 → 701 广州`（干线）；
- `sys_route_transfer`：`701 广州 → 440111 白云区`（直达），已授权给济南程驰所属公司。

过程：
1. O=501，R=440111；BFS：501→601→701；701 命中 E2（白云区）。
2. 唯一候选链路：`501 → 601 → 701 → 440111`，节点数 4，末段直达，总时效 = 短驳 + 干线 + 直达。
3. 若另存在 `501 → 701` 干线，则候选 `501→701→440111` 节点数 3，排第一；原 4 节点链路排第二。
4. 若另存在 `701 → 440111` 外转路由，则同一 4 节点下直达排前、外转排后。
5. 用户选中第 1 条，保存时服务端重算并比对 `routeIds`，一致才落库。

## 7. 表结构设计（草案，不执行）

> v1.9 子母单字段：`parent_id/parent_no/is_child/child_seq` 加在运单主表，不建独立子表；`uk_parent_child` 保证同一母单下子单序号唯一（母单 `parent_id IS NULL` 可多行）；`idx_parent_no` 支持按母单号查子单。
>
> v1.11 网点字段：逻辑 2 项（始发网点、运达网点），物理 **4 列**（`origin_hub_id/origin_hub_name`、`dest_hub_id/dest_hub_name`）。id 存 `sys_dept.id` 用于归属统计与权限，名称快照用于列表/导出/打印；两列均**只读派生**，由路由结果写入，不接受前端手填，也不提供人工修改入口（Q29）。`origin_hub_id` 默认等于 `dept_id`（同为开单网点），但保留独立列，避免"归属机构"与"发货网点"语义绑死，并支撑跨网点揽收统计。索引 `idx_origin_hub`、`idx_dest_hub` 支撑按网点筛选与统计。
>
> v1.8 字段核对：货物明细在本表只落 `quantity`（件数）、`weight`、`volume` 三列，`volume` 已改为必填；`unit_price` / `subtotal` 从未建列，数量列随本次调整从原型与字段清单删除，无需额外 ALTER。

索引理由：
- `uk_waybill_no`：运单号全平台唯一，并发兜底；
- `uk_pre_order_no`：一条预开单只允许生成一张运单；MySQL 唯一索引允许多个 NULL，普通自行开单不受影响；
- `idx_related_no`、`idx_customer_name`、`idx_sender_phone`、`idx_receiver_phone`：列表高频检索；
- `idx_dept_time`：数据权限 + 默认按开单时间倒序的分页主路径；
- `idx_dest`：按目的地省/市/区县筛选与统计；
- `idx_origin_hub`、`idx_dest_hub`：按始发/运达网点筛选、排序与网点维度统计（v1.11）；
- `idx_status`、`idx_pay_method`：状态与支付方式筛选；
- `idx_create_by`：数据权限档位 5（仅本人）；
- `idx_sales`：业务员筛选。

```sql

                   COMMENT '最后修改时间',
  `deleted`        TINYINT(1)   NOT NULL DEFAULT 0

  KEY `idx_name` (`customer_name`),
  KEY `idx_phone` (`contact_phone`),

  KEY `idx_status` (`status`)

  COMMENT='简易客户表：仅承载开单与运单当前需要的客户名称、电话、地址、状态与归属机构；客户管理模块后期在此基础上补全，不预置信用、等级等未使用字段';
```

设计理由：
- **只放真正被使用的字段**：名称、电话用于选择与联系；地址用于辅助；状态用于停用；归属机构用于数据权限。不预置客户等级、信用额度、结算方式等，避免过度设计。
- **不建客户编码**：当前选择器用"名称（电话）"即可区分，编码等客户管理模块再定；运单不依赖客户编码。
- **不做全局唯一索引**：逻辑删除后同名客户需要可重建；同机构重名由应用层校验。
- **与运单的关系**：运单存 `customer_id` + `customer_name/customer_phone` 快照。既保留可追溯的客户主数据关联，又保证客户改名/停用/删除后历史运单展示不变。
- **后期扩展兼容**：客户管理模块可在本表加字段（等级、结算方式、开票信息、多联系人子表等），运单表不需要改；若客户需要跨公司共享，再增加共享关系表，运单快照不受影响。
- **可见性**：本期按 `dept_id` 参与数据权限，A 公司创建的客户默认只有 A 公司及下级可见；是否跨公司共享由后续客户管理模块决定。

```json
    {"id": 1002, "no": "YD20261123000126-01", "seq": 1, "status": 30, "quantity": 10, "weight": 120.500, "volume": 1.200},
    {"id": 1003, "no": "YD20261123000126-02", "seq": 2, "status": 30, "quantity": 8, "weight": 80.000, "volume": 0.800}
  ]
}
```

| 规则 | 内容 |
|---|---|
| 必填对象 | `waybill{id,no,status,parent_id,parent_no}` 五项齐全；`children[]` 无子单时写空数组，不得省略 |
| 子单字段 | `children[{id,no,seq,status,quantity,weight,volume}]` 七项齐全，来自动作前后的实际状态 |
| 快照必填 | action_type 1/2/3/4/5 **五类动作均必须写** `before_snapshot` 与 `after_snapshot`，DDL 为 `JSON NOT NULL` |
| 原因必填 | **3 撤销拆单、4 作废、5 强制签收必须写 `reason`**；1 拆单、2 合单可空 |
| 日志归属 | 所有日志统一挂**母单**：`waybill_id`=母单ID、`waybill_no`=母单号；子单相关动作不单独挂子单 |
| 查询口径 | **本期只支持按母单查询**（`waybill_id`/`waybill_no`）；不提供按子单号反查日志的索引与接口，需查子单相关记录时先按母单查、再在 `children[]` 中过滤（限制写入本节，后续如需子单维度检索再评估加列/加索引） |

设计理由：
- **统一审计落点**：拆、合、撤、作废、强制签收都是低频但责任敏感的动作，原因不塞进 `biz_waybill.remark`，避免业务备注与审计原因混淆；
- **前后快照用 JSON**：不同动作关注字段不同，固定结构统一为 `waybill + children[]`，保留动作前后状态，便于追溯与客服解释；查询仍以 `waybill_id/waybill_no/action_type` 为主；
- **原因与快照分级**：撤销/作废/强制签收风险最高，强制填原因；拆单/合单为常规操作，原因可空；五类动作都要求前后快照，保证可还原；
- **不建物理外键**：与全库一致，`waybill_id` 逻辑引用；运单逻辑删除后日志仍保留；
- **数据权限**：按 `dept_id` 过滤，总部可跨机构查询；分公司是否应看到总部对本公司运单的操作记录为**待定项 Q30**，留到权限细化阶段处理（v1.14/S2，当前实现不变）。

## 8. 运单号编号规则与并发唯一性

### 8.1 编码规则（建议，待 Q8 确认）

```
运单号 = "YD" + yyyyMMdd + 6 位日内流水（不足左补 0）
示例：YD20261123000123
长度：固定 16 位
```

理由：
- 全平台唯一，不含网点编码，避免网点编码变更、编码过长、跨公司冲突；
- 前缀 `YD` 易识别、易口头报号；日期段便于人工排序与按天归档；
- 6 位日容量 999,999 单，远超单日业务量；达到 80% 时日志告警；
- 固定长度便于打印、条码与索引。

不采用"网点编码 + 日期 + 流水"的原因：网点编码最长 50 位、含下划线，打印与口头识别差；且跨网点重号风险需要额外拼接规则。若家伟坚持要含网点，见 Q8 备选。

### 8.2 并发分配（不依赖 Redis，项目当前无 Redis 依赖）

使用 `biz_waybill_no_seq` 单行原子自增：

```sql
-- 第一次分配：插入当日行并把 current_val 设为 1
INSERT INTO biz_waybill_no_seq (seq_date, current_val)
VALUES (CURDATE(), LAST_INSERT_ID(1))
ON DUPLICATE KEY UPDATE
  current_val = LAST_INSERT_ID(current_val + 1);

-- 同连接立即取回本次分配值
SELECT LAST_INSERT_ID();
```

要点：
- `LAST_INSERT_ID(expr)` 在 `ON DUPLICATE KEY UPDATE` 中把表达式值写入会话变量，多实例并发安全；
- 分配与运单插入在同一事务内；事务回滚会浪费一个号（允许跳号，不要求连续）；
- `uk_waybill_no` 唯一索引作为最后兜底；若仍冲突，重试一次分配，第二次失败则返回 `500` 并记录日志；
- 不预分配号段、不使用内存计数，避免多实例重复；
- 每日行数很小（365 行/年），无需清理；可保留 3 年后归档。

### 8.3 安全与审计

- 运单号创建后不可修改；编辑接口忽略 `waybillNo` 字段；
- 作废不释放号，不复用；
- 导入运单（后续模块）如需外部单号，写入 `related_no`，不占用运单号序列。

### 8.4 预开单号规则（v1.1 新增）

```
预开单号 = "YJ" + yyyyMMdd + 6 位日内流水（不足左补 0）
示例：YJ20261123000123
长度：固定 16 位
```

- 与运单号同一套分配机制，独立计数：新增 `biz_pre_waybill_no_seq`（结构同 `biz_waybill_no_seq`，`PK(seq_date)`），不共用运单流水表，避免预开单消耗运单号或反之。
- 由客户端提交接口在服务端生成，客户端不得自造；`uk_pre_order_no` 唯一索引兜底。
- 预开单号创建后不可修改；撤单不释放号。

### 8.5 预开单号 / 运单号 / 关联单号的关系

| 编号 | 何时产生 | 存储位置 | 是否可空 | 用途 |
|---|---|---|---|---|
| 预开单号 `YJ…` | 客户端提交预开单时 | `biz_pre_waybill.pre_order_no`；生成运单后同时写 `biz_waybill.pre_order_no` | 自行开单为空 | 追溯来源；一单只生成一张运单 |
| 运单号 `YD…` | 确认揽收/自行开单保存时 | `biz_waybill.waybill_no`；回写 `biz_pre_waybill.waybill_no` | 运单必有 | 正式单据号，打印/对账/查询主键 |
| 关联单号 `related_no` | 开单员手工录入 | `biz_waybill.related_no` | 可空 | 客户/上游系统单据号；与预开单号无关，不互相覆盖 |

- 三者互不兼职：**不得**把预开单号写入 `related_no`，否则客户单号与内部预开单会混淆。
- 展示口径：运单详情顶部显示"关联单号 / 来源预开单号"两项；预开单号为空时显示 `-`。
- 查重口径：同一 `pre_order_no` 只允许一张有效运单，由 `uk_pre_order_no` 保证；`related_no` 允许重复。

- 状态只能按矩阵前进，禁止跳级与回退；**母单 25/30/40/55/60/70 由有效子单汇总，不允许手工推进**（v1.9，规则见 3.4.5）；**唯一例外是 Q28 强制签收**：50/55 时可由有权限人员填写原因后置 60；

- 状态变更必须记录操作人与时间；拆单、合单、撤销拆单、作废、强制签收**均写前后快照**到 `biz_waybill_log`（7.6），其中撤销拆单/作废/强制签收**必填原因**，拆单/合单原因可空；轨迹类明细归签收/轨迹模块。

### 9.3 与其他模块的衔接预留

- `wait_notice=1`：到货后进入"等通知"池，不自动派送（后续模块读取该标记）；
- `need_receipt=1`：进入回单管理待办（后续模块读取）；
- `cod_amount>0`：进入代收货款台账（财务模块读取）；
- `status` 变更由后续模块负责，本方案只保证初始状态与作废。

### 10.1 参与过滤的业务表

| 表 | 是否参与 | 锚点 | 说明 |

### 10.2 四档落点

锚点：当前机构 `currentOrgId` → 无则回落用户主机构 `sys_user.dept_id`。

| 档位 | 运单列表可见范围 | 预开单列表可见范围 | 说明 |
|---|---|---|---|
| 1 全部 | 全部运单 | 全部预开单 | 超管/总部全局角色 |
| 3 本机构 | `dept_id = 当前机构` | `dept_id = 当前机构` | 只看当前机构开的单/待接单，不含下级网点 |
| 4 本机构及以下（默认） | `dept_id IN (当前机构 + 全部子孙机构)` | 同左 | 分公司管理员默认档位，能看本公司及下属网点 |
| 5 仅本人 | `create_by = 当前用户ID` | `accept_by = 当前用户ID OR (status=10 AND dept_id=当前机构)` | 见下方例外说明 |

- 客户表同理；客户在当前范围内才能被选择。
- **档位 5 的预开单例外**：预开单尚未被接单时 `accept_by` 为空，若严格按"仅本人"过滤，开单员将看不到任何待接单，业务无法开展。因此档位 5 对预开单采用"本人已接单的 + 本机构待接单的"组合条件；该例外必须在 `data-permission-spec.md` 登记，并在拦截器中按表名分支处理，不能全表通用。
- 确认揽收生成的运单，其 `create_by` 为当前接单人，档位 5 下本人可见；若由网点管理员接管并确认，运单 `create_by` 记为管理员，原接单员在档位 5 下看不到该运单，需管理员或更高档位查看。
- 数据权限过滤开关当前 `yunshu.data-scope.enabled=true`，本模块上线前必须完成拦截器实测（探针表方式，参照 2026-11-21 的验证方法）。
- 档位 2（自定义机构）仍拒绝写入，不实现。

### 10.3 开单侧接入点

1. **开单网点（v1.15）**：固定取账号当前机构（顶部机构切换后的那个机构），页面**只读展示**、不提供下拉；`GET /depts/manage-scope` 可选网点接口保留但开单页不再调用；服务端保存时同样以当前机构为准，忽略客户端传入的 `originDeptId`。
2. **公司判定 C**：当前机构向上最近的 `dept_type=2`；无则总部。用于路由授权过滤（见 6.4）。
3. **保存归属**：`dept_id` 由数据权限自动填充为当前机构；`create_by` 自动填充为当前用户；`dept_name` / `create_by_name` 由服务层取当前机构/用户名称快照。
4. **机构切换**：开单页跟随 `currentOrgId` 变化刷新开单网点并清空已选目的地/线路；提交时服务端以当时的当前机构为准，不缓存旧机构。
5. **前端不传 `dept_id`**：接口不接受客户端指定归属机构，防止伪造；即使传了 `originDeptId` 也被忽略。

### 10.4 运单管理侧接入点

1. 列表、详情、导出、合计行**必须复用同一查询条件**（同一 mapper/wrapper），由拦截器自动追加 `dept_id` 条件。
2. 详情、编辑、作废前显式调用 `dataScopeGuard.assertReadable/assertWritable`，越权返回 403 文案，不泄露记录是否存在。
3. 当前机构切换后：清空列表、筛选、分页，重新请求；标签页保留，不混用新旧数据。
4. 导出按当前可见列 + 当前筛选 + 当前排序，行序与列表一致。
5. 客户下拉同样走数据权限，不允许跨公司选客户。
6. 运单号查询不绕过权限：即使知道运单号，也只能查到范围内的单。

## 附录 A（V14 结构扩展，2026-11-23 家伟批准）

> 本附录为已批准的结构扩展落地口径，不改变正文既有字段语义；实际迁移见 `backend/src/main/resources/db/migration/V14__operation_waybill_goods.sql`。

### A.1 新增表 `biz_waybill_goods`

- 字段：`id`、`waybill_id`、`seq`、`goods_name`、`goods_type`、`package_type`、`quantity`、`weight(12,3)`、`volume(12,3)`、`goods_remark`、`dept_id`、`create_by`、`create_time`、`update_by`、`update_time`、`deleted`。
- `quantity/weight/volume` 不设默认值，必须显式传值；服务层校验 `quantity>=1、weight>0、volume>0`。
- 唯一键 `uk_waybill_seq(waybill_id, seq)`；索引 `idx_waybill`、`idx_dept`。
- `dept_id` 与运单一致，参与数据权限过滤。

### A.2 `biz_waybill` 新增列

- 发货单位 `sender_company`、收货单位 `receiver_company`（均 `VARCHAR(100)`，可空）。
- 收货省/市/区县按项目既有区划风格拆为 `code + name` 成对，共 6 列：`receiver_province_code/name`、`receiver_city_code/name`、`receiver_district_code/name`；编码统一 `VARCHAR(12)`、名称 `VARCHAR(64)`，全部可空、无默认值。
- 因此需求清单中的“发货单位/收货单位/收货省/收货市/收货区县”5 项，实际物理列为 8 列。

### A.3 子表与主表汇总关系

- 主表 `quantity/weight/volume` 不再由客户端直接决定：服务端按子表行汇总后写入主表，二者始终一致。
- 若客户端显式携带主表三量，服务端会与明细合计逐项比较；不一致直接 400 拒绝（篡改检测），一致则按汇总值落库。
- 子表与主表同事务写入；运单详情同时返回主表、路由节点与货物明细行。

### A.4 收货省市区县与收货地址一致性口径（建议：仅提示，不强拦截）

- **前端**：已选收货省/市/区县且填写收货地址后，若地址文本既不含所选市名也不含区县名，展示黄色提示“收货地址未包含所选城市/区县名称，请确认（仅提示，不影响保存）”。
- **后端**：只校验三码齐全与层级关系（省 → 市 → 区县均存在且 `parent_code` 逐级匹配），并派生名称快照；**不解析收货地址文本、不做强拦截**。
- **理由**：收货地址是自由文本，常见园区名、简称、门牌号写法，文本强匹配误拦概率高；区划编码已保证行政归属准确，地址文本用于派送补充。若后续需要强一致性，应引入结构化地址或地址库校验，而不是字符串包含判断。
